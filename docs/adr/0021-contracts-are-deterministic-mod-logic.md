# Contracts are deterministic mod logic; Claudia does language and judgement

Everything computable about Contracts is deterministic mod logic in the Adapter and Core: reading Contracts, recognising Contract Requirement kinds, pricing and choosing the set, building the Contract Route, checking Claudia's plan, watching Requirement state, timing test actions, and every chat line the mod posts. Claudia does language and judgement: the player's typed words, writing the Mission Plan from the Contract Route, explaining choices, and replanning in Debriefs. Contract Requirement kinds Core doesn't recognise are reported "not yet", never improvised. Decided with the spec for Contract-driven Missions in Career (#1021).

- **Reading (Adapter, main thread).** The Adapter lists the accepted Contracts and walks each Contract Requirement tree generically, since the tree's shape varies within one type (a haul PartTest has its conditions beside the PartTest Requirement, a test has them under it). Settings come from each Contract's and each Requirement's own saved form, `Save(ConfigNode)`, which writes the save file's keys: never private fields, which mods read by reflection at a field index and which break silently when KSP reorders them. State, the optional flag, the deadline (absolute game time once accepted), the completion rewards after the game's own Strategy query, the active-Contract limit for the Mission Control level and the active count come from the game's public members. The mod never accepts, declines or cancels a Contract.
- **Keys.** The game has no id for a Contract Requirement and rebuilds every Contract object on each load and scene change, so nothing holds a game object. A Requirement's key is its Contract's GUID and its position in the tree (`ContractRequirement.KeyOf`: the index at each level from the top), as kRPC does.
- **Plain data.** Core sees Contracts only through the Game Snapshot (`SnapshotContracts`), as it sees the craft. Claudia never reads the live game. A Career save with no accepted Contract, and Science and Sandbox saves, give a snapshot exactly as before.
- **Classification by the game's names.** Core recognises a Requirement by the game's kind name and its saved settings, never by its title, which is localised.
- **Fixtures from real play.** The capture button writes a Game Snapshot per accepted Contract beside the whole one; recorded in a 1.12 career, these are Core's test fixtures for each stock type, as recorded snapshots are for the craft.

We rejected letting Claudia read the Contracts and plan them herself: the settings are machine-readable for every stock kind seen, so reasoning would add cost and a chance of a wrong plan where a table is exact. We rejected the typed private fields for settings, as above.
