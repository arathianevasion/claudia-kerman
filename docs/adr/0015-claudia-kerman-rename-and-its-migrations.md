# Claudia Kerman: the rename from Kermin and its migrations

The player decided on 2026-11-02 that Claudia's surname is **Kerman**, the stock Kerbal surname. Her Kerbal name, the mod's name and every identifier now use it: `ClaudiaKerman.sln`, the `ClaudiaKerman.*` projects and namespaces, `ClaudiaKerman.dll` with `KSPAssembly("ClaudiaKerman")` (the kOS addon's `KSPAssemblyDependency` names it), `GameData/ClaudiaKerman`, the log tag `[ClaudiaKerman]`, dialog ids and Harmony ids. The trait `SuperIntelligence`, `ADDONS:CLAUDIA` and her first name are unchanged. Nothing the player has is lost; `RenameMigration` in Core holds the old names and the moves, and is the only code that spells "Kermin":

- **The config folder.** On the first resolve of a session, `ConfigDirectory` moves `ClaudiaKermin` (under `~/Library/Application Support`, `%APPDATA%` or `$XDG_CONFIG_HOME`) to `ClaudiaKerman` when only the old one exists. It is a rename, so the API key and `config.cfg` move with their owner-only modes, and the key works without being entered again. When both exist the new one is used and the old one is left alone. A failed move keeps the old folder in use for the session and logs once.
- **Mission folders.** Each time a save loads, the adapter moves `saves/<save>/ClaudiaKermin` to `ClaudiaKerman` the same way, before the core reads the Missions, so transcripts, `mission.json`, `events.jsonl` and snapshots carry over and past Missions stay in the Missions list. A folder that couldn't move is still read in place (`MissionFolder.Root`).
- **Her crew entry.** The roster planner finds a Kerbal named "Claudia Kermin" by her trait, or by that name when a mod changed her trait, before the name-clash check, so her own old entry is never a clash. It renames her with the existing `RevertName` action (`ProtoCrewMember.ChangeName`), which keeps her stats, experience, flight log and seat. Until it runs, a Game Snapshot counts the old name as hers. No Mission state stores her name.
- **The save file.** KSP finds `SCENARIO` nodes by class name, not assembly or namespace (the driver reads them by `typeof(MissionScenario).Name`), and the mod has no part modules, so the scenario nodes load as they are. The Claudia Flag's old URL (`ClaudiaKermin/Flags/ClaudiaFlag`) no longer loads: on load, the agency flag and every vessel's parts and planted flags that fly it take the new URL. Prepare to uninstall goes by trait, so it works on old saves.
- **The old GameData folder.** With `GameData/ClaudiaKermin` installed beside the new folder, both copies would load and fight over her name. The new one stands down (no Loader, no roster changes), logs an error and shows one dialog at the main menu telling the player to delete the old folder. A save made in that state keeps its Missions: `MissionScenario` writes back what it loaded.

Kept on purpose: the GitHub repo (`arathianevasion/claudia-kermin`) and the local checkout folder, which the player renames separately; recorded Missions and transcripts that quote the old name (`benchmarks/interplanetary`), since they are what was sent then; and the old Mission's frozen system prompt, which a resumed Mission keeps byte for byte for the cache. The cost tools read both folder names. The prompt text changed by the same number of characters, so the prefix estimate is unchanged.

We rejected keeping the old identifiers behind new display text (two spellings for good) and a compatibility copy of the old GameData folder (that is the duplicate install the guard refuses). The cost: a little migration code and its tests, kept until no old installs remain.

Decided on #665.
