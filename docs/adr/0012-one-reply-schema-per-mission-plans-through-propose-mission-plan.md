# One reply schema per Mission; Mission Plans arrive through `propose_mission_plan`

Every Mission request, from the first Mission Plan to the end of the Mission, sends the same structured-output schema, the same tools list and `tool_choice` `auto`. The schema takes every reply kind (`mission_plan`, `sequence_plan`, `debrief`, `answer`, `alert`) and carries the Sequence Plan, Debrief and Alert parts, each nullable. It has no Mission Plan part: a Mission Plan arrives through **`propose_mission_plan`**, a non-strict Reply Tool that is always in the Mission's tools list.
- **The tool:** its input is the Mission Plan part, with the same fields and meaning as before. The mod checks it with the existing parsing and plan checks (the schema, and Child Vessels that never left the craft) and answers ok or the problems, the way `check_script` answers. Claudia can fix the plan and call again in the same turn.
- **The reply:** Claudia ends the turn with `kind: "mission_plan"`, `say`, `reply_intent` and `unsure_because`. The mod takes the last plan the tool accepted in that turn. With none, the reply is refused as `off_schema` and the usual retry runs. The same is true when the tool loop ends without an accepted plan; the step before the tool limit asks for the plan.
- **When the tool works:** only on a request that can come back as a Mission Plan: the first or a revised plan, a reduced goal, the Mission Settings, and the player's typed Reply or Change. Anywhere else it returns an error, as `check_script` does during an Alert. During a flight a typed Reply or Change takes a plan only with a new Mission Goal.
- **The kind still has to fit.** The schema allows every kind, so `Mismatch` refuses one that doesn't fit the request's Purpose (a Reply or Change that comes back as a Debrief or an Alert, for example), reported as `off_schema`. The request's notice says which kind to send.

This replaces #199's reasoning. #199 split the reply schema in two (planning and flight) because one schema with every part went over the API's internal grammar limit ("compiled grammar is too large"). But a changed schema rewrites nearly the whole prompt cache. On mission f623, three Flight-to-Planning switches, each a revised Mission Plan after an Off-Nominal Debrief, cost about $2.2 of $7.55. A typed reply during a flight did the same, and on b5f3 the switch cost $0.56 of $2.20 (spec #565).

We chose a Reply Tool over the alternatives for these reasons:
- **The grammar fits.** A non-strict tool's input schema is not compiled into the output grammar. The SchemaProbe `mission-grammar` probe (2026-10-31, claude-haiku-5-5 and claude-sonnet-5-5) sent the one Mission schema (size 80, 3 unions; `tools/ClaudiaKermin.SchemaProbe/schemas/534-mission.json`) both with `propose_mission_plan` in the 8-tool list and without it: both compiled. `MissionReplySchemaTests` holds the size budget at 80, the largest size probed to compile. Every part in one schema (size 98) is still over it.
- **No schema switch.** We also considered a different schema for each Purpose, or one schema with sentinels instead of parts. Either changes the request between kinds, or was refused at #199.
- **The plan is checked before the player sees it.** Claudia gets the mod's problems back while she is still planning, instead of losing a whole turn to a refused plan.

What else we probed, and why only the schema and tools are held fixed (#534 item 6). The SchemaProbe `cache-probe` (2026-10-31, both models, about 39k tokens of conversation history) read the full cache back after changing only the top-level `effort`, only `tool_choice` from `auto` to `none`, and `effort` by a mid-conversation system message. So `EffortFor` per Purpose stays, the Second look's and the cut-off retry's raised effort stays, and #509's last tool-loop request keeps `tool_choice` `none`. The byte-identity test pins `output_config.format`, `tools` and `tool_choice` on ordinary requests, but not `effort`.

The costs:
- **The prefix grows** by `propose_mission_plan`'s definition: 2,388 characters, about 796 tokens by the mod's estimate (MissionPrefixBudgetTests: 20,534 to 21,330, under its 21,500 budget). It is read from the cache on every request and written once.
- **Each Mission Plan turn takes one more request.** The tool call, then the short final reply. That request reads the conversation from the cache and adds about 60 output tokens. The plan's own tokens move from the reply into the tool input.
- **Old saves need no migration.** `MissionReply.Parse` still reads a Mission Plan part written inline, so transcripts and saves from before load as they did. The first request after loading one rewrites the cache once.

Decided on #534 (spec #565); replaces the two-schema split of #199.
